things I believe about backends

  1. An auth rule that is not enforced on the server is just a feature suggestion.
  2. If the server never sees plaintext, it can't leak plaintext.
  3. "All tests pass" means nothing until you know what the tests would have caught.
  4. Schemas outlive code. Migrate them like you mean it (Flyway).
  5. Write the honest number in the README, even when it is less impressive.

CASE 01 · SAFETY

TwinGuard

A release gate for over-the-air car updates.

BLOCKED

A media-player update passes all 48 conventional tests, but gives audio the same network priority as radar. Under load, the brakes hear about the obstacle too late. TwinGuard runs v1 and v2 side by side in a simulated car, searches thousands of scenarios, shrinks each failure to the simplest one that still fails, then measures how far its own verdict can be trusted by planting bugs and counting catches.

CASE 02 · SECURITY

KeyVault

A zero-knowledge secrets & API-key manager.

CONFIDENTIAL

hover the black bars to decrypt →

Plaintext secrets never touch the server. Keys are derived with PBKDF2 (100k rounds) and encrypted with AES-256-GCM inside the browser or the CLI. The database stores only ciphertext, salts and IVs.

  • RBAC per workspace: owner · admin · member · viewer
  • Immutable version history, one-click rollback
  • Scoped machine tokens for CI pipelines
  • kv-cli run --env prod -- npm start injects secrets in memory, so no .env file is ever written to disk
  • Audit trail, rate limiting, token blacklist, expiry e-mails
  • Spring Boot 3.2
  • Java 17
  • MySQL 8
  • Web Crypto
  • Node CLI
